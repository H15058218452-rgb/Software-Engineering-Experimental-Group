## 1. 统一约定（所有人必须遵守）

1. 响应结构统一：`{ "code": 0, "message": "success", "data": {...} }`，code=0 成功，非 0 失败。
2. 前端只按 code 弹提示，不自己判断业务状态。
3. 金额是字符串（如 "99.90"），禁止用 JS number 直接算。
4. 所有 ID 是字符串（后端 Long 转 String）。
5. 时间 ISO 8601（带 +08:00）。
6. 卖家接口统一带头：`Authorization: Bearer <token>`。
7. 买家口令码：提交意向时返回一次，之后查询/修改/撤销都传 code。
8. 写接口可传 requestId 做幂等（防重复点击），后端已支持。

错误码速查：40001 参数错误 / 40101 未登录 / 40301 无权限 / 40401 资源不存在 / 40901 并发冲突 / 40902 商品已冻结 / 40903 商品已下架 / 40904 重复提交意向 / 40905 口令码无效 / 40906 意向状态不允许 / 40907 非队首 / 40908 交易中不可解冻 / 40909 交易中不可下架 / 40910 交易中不可撤销 / 40911 类别不合法 / 40912 同级类别重名 / 40913 类别下还有子类别 / 40914 类别下还有商品 / 40915 库存不足 / 40916 库存不能为负 / 40917 商品图库最多 9 张 / 50000 系统错误。

## 2. 给前端童昕祺（买家端，免登录）

| 接口 | 方法 | 地址 | 入参 | 返回 |
|---|---|---|---|---|
| 当前商品 | GET | /api/buyer/product/current | 无 | ProductView（含 canSubmitIntent） |
| 提交意向 | POST | /api/buyer/intent | name, phone, productId?, requestId? | { code, intent }，code 只显示一次 |
| 查询意向 | GET | /api/buyer/intent?code= | code | BuyerIntentView |
| 修改意向 | PUT | /api/buyer/intent | code, name?, phone? | BuyerIntentView |
| 撤销意向 | POST | /api/buyer/intent/cancel | code | 无 |

关键点：
- 商品无数据时 current 返回 data=null，前端展示"暂无商品在售"。
- canSubmitIntent=true 才可提交；商品冻结/交易中时返回 false 且提交会得到 40902。
- 提交成功拿到 code 后必须引导用户保存（只显示一次）。
- 查询时 queuePosition 是当前排队位次；canModify / canCancel 决定按钮是否可点（后端返回，前端别自己推）。
- **迭代 2：`/api/buyer/product/current` 只保留做兼容，列表页请改用第 7 节的 `/api/buyer/products`，提交意向必须带 `productId`。**

## 3. 给前端陈泽英（卖家后台，需 token）

| 接口 | 方法 | 地址 | 入参 |
|---|---|---|---|
| 登录 | POST | /api/seller/login | username, password |
| 改密码 | POST | /api/seller/change-password | oldPassword, newPassword（>=8位） |
| 发布商品 | POST | /api/product/publish | name, categoryId, description?, price, stock?, images?, requestId? |
| 手动冻结 | POST | /api/product/freeze | productId, requestId? |
| 手动解冻 | POST | /api/product/unfreeze | productId, requestId? |
| 开始交易 | POST | /api/product/start-trade | productId, requestId? |
| 确认成功 | POST | /api/product/confirm-sold | productId, intentId, requestId? |
| 确认失败 | POST | /api/product/confirm-failed | productId, intentId, disposition(VOID/REQUEUE), requestId? |
| 手动下架 | POST | /api/product/off-shelf | productId, requestId? |
| 当前商品 | GET | /api/seller/product/current | 无 |
| 意向列表 | GET | /api/seller/intents?productId= | productId |
| 历史商品 | GET | /api/seller/history/products?page=&pageSize= | 分页 |
| 历史意向 | GET | /api/seller/history/products/{id}/intents | id |
| 图片上传 | POST | /api/upload/image | multipart 字段 file |

关键点：
- 登录拿 token 后，所有接口带 Authorization: Bearer <token>。
- 卖家当前商品视图（SellerProductView）里带 5 个按钮标志：canFreeze / canUnfreeze / canStartTrade / canOffShelf / canConfirmTrade，前端按这些标志控制按钮显隐和禁用，别自己判断状态。
- 发布商品前先调上传接口传图，拿到 /uploads/xxx 填进 images（或 imageUrl）。
- confirm-failed 必须带 disposition，值只能是 VOID 或 REQUEUE。
- **迭代 2：发布必须带 `categoryId`（二级类别），`/api/seller/product/current` 只保留做兼容，管理页请改用第 7 节的 `/api/seller/products`。**

## 4. 给后端李炫苇的对接

你负责意向表、卖家表、图片上传、SQL、API 联调。现状：杜美芳为了让后端能跑通，已临时把这三块一并实现了。你们二选一：

方案一（推荐）：杜美芳保持现状，李炫苇专注出 SQL 脚本和组织联调测试；Postman 集合、Dockerfile 由胡芷源负责。
方案二：李炫苇接管 intent/seller/上传三块的代码维护，杜美芳移交。

无论哪个方案，必须沿用以下已定的表结构与枚举（否则联调必炸）：

- product 表：status TINYINT（0 在售 / 1 手动冻结 / 2 交易中冻结 / 3 已下架）、current_intent_id、price DECIMAL(10,2)、**stock INT（库存，>=0，成交扣减、归零自动下架）**、**category_id BIGINT（二级类别）**、**images_json TEXT（图库 JSON 数组，≤9 张）**、**description MEDIUMTEXT（富文本 HTML）**。**迭代 2 已移除 active_flag 生成列与 uk_product_active 唯一索引，不再有单活跃商品约束。**
- category 表（迭代 2 新增）：id、name、parent_id（NULL=一级）、sort，固定两级。
- intent 表：status TINYINT（0 排队中 / 1 交易中 / 2 成功 / 3 作废 / 4 撤销 / 5 重新排队中 / 6 最终失败）、code_hash CHAR(64)、queued_at DATETIME(3)、fail_count
- seller 表：username 唯一、password_hash（BCrypt）
- 完整 DDL 见 src/main/resources/schema.sql；从基线库升级见 src/main/resources/migration-a.sql（幂等，启动自动执行）

## 5. 联调顺序（建议按此推进）

1. 杜美芳启动后端，确认 Swagger 可开、schema.sql + migration-a.sql 执行成功。
2. 李炫苇组织按第 2/3 节接口逐个过一轮；Postman 集合由胡芷源汇总产出。
3. 童昕祺接买家端：先做"浏览商品 + 提交意向 + 拿口令码"，再做查询/修改/撤销。
4. 陈泽英接卖家端：先做"登录 + 发布商品"，再做冻结/解冻/开始交易/成交/下架。
5. 全员联调一条完整链路：发布 -> 3 个买家提交意向 -> 开始交易 -> confirm-failed 递补 -> confirm-sold 下架 -> 历史记录。
6. 出问题时，前端把响应里的 traceId（X-Request-Id 头）报给后端排查。

## 7. 迭代 2（挑战需求 A）新增 / 变更接口

> 后端已全部实现并编译通过，可直接联调。

### 7.1 类别（A.1-2）

| 接口 | 方法 | 地址 | 鉴权 | 入参 | 说明 |
|---|---|---|---|---|---|
| 类别树 | GET | /api/category/tree | 公开 | 无 | 返回两级树，一级带 children，children 含空列表 |
| 新建类别 | POST | /api/seller/category | 卖家 | name, parentId?, sort?, requestId? | parentId 为空=建一级；非空=在其下建二级 |
| 修改类别 | PUT | /api/seller/category/{id} | 卖家 | name, sort?, requestId? | |
| 删除类别 | DELETE | /api/seller/category/{id} | 卖家 | 无 | 有子类→40913；有商品→40914 |

规则：固定两级，给二级类别建子类会被拒绝（40911）；同级重名 40912。

`GET /api/category/tree` 返回示例：

```json
{
  "code": 0,
  "data": [
    { "id": "1", "name": "服装", "parentId": null, "sort": 0,
      "children": [ { "id": "2", "name": "女装", "parentId": 1, "sort": 0, "children": [] } ] }
  ]
}
```

### 7.2 卖家商品管理（A.1-1 / A.1-3 / A.1-5）

| 接口 | 方法 | 地址 | 入参 | 说明 |
|---|---|---|---|---|
| 商品列表 | GET | /api/seller/products | status?, categoryId?, keyword?, page=1, pageSize=10 | 含已下架；status 不传=全部 |
| 商品详情 | GET | /api/seller/products/{id} | 无 | 含富文本正文与图库 |
| 发布商品 | POST | /api/product/publish | name, categoryId, description?, price, stock?, images?, requestId? | 可同时发布多件 |
| 编辑商品 | POST | /api/product/update | productId, name, categoryId, description, price, images, requestId? | 交易中禁止编辑 |
| 手动下架 | POST | /api/product/off-shelf | productId, requestId? | 交易中 40909 |
| 重新上架 | POST | /api/product/shelf-on | productId, requestId? | 仅已下架且库存>0 |
| 补货 | POST | /api/product/restock | productId, quantity, requestId? | 只加库存，不改状态 |
| 调整库存 | POST | /api/product/stock-adjust | productId, delta, requestId? | delta 可负；不得为负（40916）；减到 0 自动下架 |

发布/编辑参数说明：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| name | string(255) | 是 | 商品名称 |
| categoryId | number | 是 | 必须是二级类别，否则 40911 |
| description | string | 否 | 富文本 HTML，后端做白名单清洗后入库 |
| price | string/number | 是 | >0，最多 8 位整数 2 位小数 |
| stock | number | 否 | 默认 1，发布时 >=1 |
| images | string[] | 否 | 图库，最多 9 张，第一张为主图；每个地址必须是 `/uploads/xxx` 或 http(s) |

商品状态语义（前端按 status 显示标签）：`0 在售 / 1 手动冻结 / 2 交易中 / 3 已下架`。

库存规则（A.1-3，演示按此走）：
1. 发布库存 2 → 成交 1 次变 1，商品仍在售；
2. 再成交 1 次变 0 → **自动下架**，队列其余意向置为「最终失败」；
3. 补货（restock）只加库存，商品仍是已下架；
4. 卖家调 `/api/product/shelf-on` **手动上架**，商品回到在售。

### 7.3 买家浏览与搜索（A.1-4 / A.1-5）

| 接口 | 方法 | 地址 | 入参 | 说明 |
|---|---|---|---|---|
| 商品列表 | GET | /api/buyer/products | categoryId?, keyword?, page=1, pageSize=10 | 只返回在售且有库存；categoryId 传一级会自动含其下二级 |
| 商品详情 | GET | /api/buyer/products/{id} | 无 | 含 images 与 description（富文本 HTML，前端直接 v-html 渲染） |

`ProductListItem` 字段：id、name、imageUrl、price、stock、status、statusText、categoryId、categoryName、createTime、imageCount。
`ProductView` 字段：id、name、description、imageUrl、price、status、statusText、createTime、offShelfTime、canSubmitIntent、categoryId、categoryName、stock、images。

### 7.4 上传（A.1-5）

| 接口 | 方法 | 地址 | 入参 | 说明 |
|---|---|---|---|---|
| 图库批量上传 | POST | /api/upload/images | multipart 字段 `files`（多个） | 一次 ≤9 张，仅 JPG/PNG，单张 ≤5MB |
| 正文内嵌媒体 | POST | /api/upload/media | multipart 字段 `file` | 图片 jpg/png/gif/webp 或视频 mp4/webm/ogg，不限大小 |
| 单图上传 | POST | /api/upload/image | multipart 字段 `file` | 兼容基线，规则同图库 |

`/api/upload/images` 返回 `{ "urls": ["/uploads/a.jpg", "/uploads/b.jpg"] }`，顺序与上传顺序一致，直接整体提交给发布接口的 `images`。

### 7.5 提交意向的变更

`POST /api/buyer/intent` 新增可选字段 `productId`：多商品各自独立队列，前端从详情页带上当前商品 ID。不传时回退到基线行为（最近一件在售商品），仅为兼容保留。
